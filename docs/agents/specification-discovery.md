## Observed baseline

- `ApprovalService` owns Submit/Approve/Reject; approval accepts only invoice ID and username, checks PendingApproval, then immediately records Approved plus `DecidedBy` and UTC `DecidedAt`. No limits, roles or two-person records exist.
- `Invoice` stores `Id`, `CustomerName`, decimal `Amount`, `Status`, `CreatedAt`, `DecidedBy`, `DecidedAt`, and `DecisionNote`. There is no version field or approval collection.
- `ApprovalsController` admits Approver/Admin and obtains username from the authenticated server session. Role is stored in `UserSession` but is not passed into the domain. The approve action has no request body model. `RejectRequest` contains only Reason.
- Login compares configured username/password exactly and constructs a session from the matched configured account. Session bearer tokens identify server-held `UserSession` records. Browser sessionStorage contains username/role/token, but username/role there are presentation data and cannot be authorization authority.
- `ApiControllerBase.Handle` maps not-found to 404, InvalidOperationException to 409, and ArgumentException to 400 with `{ error }` messages. `RequireRoleAttribute` currently returns a bare 403, so a migrated forbidden approval path needs an explicit clear-reason contract if it counts as a rejected approval attempt.
- Invoice creation accepts any positive .NET decimal; the UI formats USD and inputs min/step 0.01. Formatting and HTML validation do not establish server precision rules.
- Both real and fake repositories return live invoice references. Real repository locks each method separately; domain reads/validates/mutates outside those locks. `Update` cannot undo mutations already made through a reference. `ApprovalService` is scoped, so an instance-local service lock would not serialize all API requests.
- UI renders every pending invoice with Approve/Reject controls for every signed-in account and shows API decision errors through an existing `role="alert"`. It has no first-approval display. A successful first approval that remains PendingApproval therefore needs a visible explanation of progress.
- Seven existing `ApprovalServiceTests` cover basic lifecycle behavior only. They assert status/selected fields and exception types; none snapshot full stored state around a rejected approval. Tests reference Domain only, so API/auth integration coverage needs deliberate project setup. `FakeInvoiceRepository.Update` is a no-op and has no concurrency boundary.
- `e2e` has a Playwright configuration and package manifest, but no existing test/page object files were found in the enumerated tree. The server config permits reuse of an existing server; tests must create uniquely identifiable invoices rather than rely on mutable seed data.

## Acceptance criteria independent of pending participant choices

1. **FR-01:** A pending invoice below or exactly 50,000 can receive final approval from a Manager. A Manager single-approver attempt immediately above 50,000 and at or below 500,000 returns a clear reason without changing any invoice/approval state. Parameterize the adjacent value using the supported increment once precision is resolved.
2. **FR-02:** A Director can finally approve a pending invoice below or exactly 500,000. Include below/equal/above boundary cases using the eventual supported increment. Amounts above 500,000 never become finally approved after only one recorded approval.
3. **FR-03:** Above 500,000, exactly one accepted eligible first approval leaves the invoice awaiting a second decision. A distinct Director can complete approval; a distinct non-Director cannot complete it. These criteria do not choose which roles qualify first.
4. **FR-04:** After any valid Director first approval, a second attempt by that same authenticated Director must fail without overwriting first-approval identity/role/time or final decision fields. Repeat using a new login/token for the same configured username: different sessions do not make distinct users. Apply the same identity rule to every eligible first role once chosen.
5. **FR-05:** For every rejected approval branch, compare an independent before snapshot with a new stored read after the error. Include all existing fields (ID, customer, decimal amount, status, CreatedAt, DecidedBy, DecidedAt, DecisionNote), all added approval identities/roles/times/notes, record ordering/count, and any version fields. Checking returned objects or Update calls alone is insufficient. Pre-seed meaningful metadata where legal so accidental clearing/overwriting is observable.
6. Rejected branches include duplicate identity, invalid second role, single-approver over-limit, unauthorized role, and invalid lifecycle state (Draft/Approved/Rejected). A missing invoice returns a clear not-found reason and creates no state. The intentional Reject operation is a separate accepted transition, not a failed Approve attempt.
7. API approval authority comes only from authenticated server state. Supplying another username/role in an approval payload or changing sessionStorage must not change the acting identity/role. Unauthenticated calls cannot approve. Domain tests directly exercise role/identity rules so UI/API restrictions cannot be the sole enforcement.
8. Concurrent requests must produce a result equivalent to a valid serial ordering. Two requests by the same user must never fill both approval positions. Competing first approvals must never overwrite or lose accepted first metadata. Concurrent final approvals may record only one final decision; losing/invalid attempts return a clear reason without overwriting that decision. Approval versus intentional rejection/delete/submit must not yield mixed or resurrected state. Assertions on a failed concurrent request must account for legitimate changes by other successful requests, using controlled schedules or linearizable outcomes rather than attributing all global changes to the failure.
9. UI verification must create a pending invoice just above the Manager limit and within the Director range, attempt approval as a Manager, see a specific reason in the alert, and reload to verify the invoice persisted unchanged. Keep the attempted action available for this required rejection scenario. Use page objects and role/label locators.
10. Preserve the separate stage-one and stage-two delegated implementation tasks and commits. Stage one must pass its own tests and fail closed for high-value final approval until stage two introduces the reviewed first/second transition. Stage two reruns the stage-one regression matrix. Preserve matching production revisions/scope for before/after mutation evidence; no score target is specified.

## Design risks and specification decisions still required

- **Participant answers pending:** eligible first approver above 500,000, including the relationship to single-approver limits; currency and supported decimal precision. Do not select adjacent monetary examples or generate dependent artifacts until those answers arrive.
- **Role migration is a proposal:** converting demo.approver to Manager, adding two Directors, and retaining Admin for administration only is not yet participant-approved. Existing Approver/Admin approvals and intentional Reject permissions need an explicit migration contract. Admin must not acquire an implicit bypass.
- **Stable identity is a proposal grounded in baseline:** canonical server-session Username can supply identity for this fixed demo account store, but configuration must not assign one logical person multiple distinct identifiers. Exact login behavior should not accidentally change through case-folding added only in the approval comparison. An identity decision is separate from token uniqueness and current role.
- **Pending representation is a proposal:** retain PendingApproval and add first identity/role/time; keep final fields unset until completion. Specify returned JSON and UI progress, retention of first metadata after final approval or intentional rejection, and behavior of retries. Storing first role at approval time avoids interpreting historical authority from a later session role.
- **Atomic mutation is a proposal:** add a repository atomic transition boundary whose callback executes domain validation and transition under the same lock. A consistent boundary must include all competing write paths; snapshots/copies or serialization under lock are needed if read APIs otherwise observe partial live-reference updates. Keep policy logic in Domain, not the repository/controller. Define the fake's matching contract and add real-repository concurrency coverage rather than trusting a serial fake.
- **Full-state immutability:** domain validation must finish before any field mutation, timestamp/version increment, or record append. If a callback can throw after mutation, the repository contract must guarantee rollback/copy-on-write or the callback must avoid that path. Error generation must not itself alter the invoice.
- **API status/error contract:** choose status codes for limit/duplicate/wrong-second-role versus coarse role denial consistently with existing Handle. All need clear visible reasons; bare role-filter 403 is insufficient for the stated failed-attempt criterion.
- **Precision enforcement placement:** after the participant decides, validate at the trusted boundary and make behavior of directly constructed domain invoices explicit. Browser Number formatting can conceal unsupported fractions; never silently round at an approval threshold unless explicitly authorized.

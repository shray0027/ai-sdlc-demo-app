## Findings

### S1-TR-01 — Reject JSON amounts before decimal conversion can round them (high)

Initial evidence: `backend/src/InvoiceApp.Api/Controllers/InvoicesController.cs:48` bound `CreateInvoiceRequest.Amount` directly to decimal and validated only the resulting value at line 55. `UsdAmount.Validate` correctly checks an already representable decimal, but framework JSON conversion can silently discard excess precision before this check.

Actual isolated live HTTP reproduction against the initial build on port 5089: login as demo.approver; create amount `50000.0000000000000000000000001`. Creation returned 201 and stored `50000.000000000000000000000000`; submit returned 200; Manager approval returned 200/Approved. Thus unsupported fractional cents were rounded into the inclusive Manager limit. Also `79228162514264337593543950335.1` returned 201 with amount `79228162514264337593543950335`. Control input `50000.0010000000000000000000000` correctly returned 400. The isolated process has been stopped.

Action: validate exact JSON numeric value before lossy decimal conversion; retain numeric trailing zeros/exponents and reject inexact or out-of-range values with 400 and no added invoice. Add API regression inputs for values rounding across the Manager/Director thresholds and decimal range boundary.

Agent verification: parent independently added `backend/src/InvoiceApp.Api/ExactDecimalConverter.cs:11`, registered at `Program.cs:15`, and added precision-rejection/exact-exponent API cases. Reviewed coefficient/exponent normalization, exact decimal equality and error mapping; the revised suite passes 95/95. This addresses the observed threshold-rounding path. Recheck: parent added decimal.MaxValue-plus-fraction as an explicit API regression; converter and all exact/invalid amount rows pass in the final reviewer run (96/96). Agent handling: addressed and rechecked. Participant verdict: **pending**.

### S1-TR-02 — Successful mutation test uses stored output as its own oracle (medium)

Evidence: `backend/tests/InvoiceApp.Tests/InMemoryInvoiceRepositoryTests.cs:23` mutates CustomerName, then line 24 captures `committed` from the repository without comparing it or the mutation result with an independent expected invoice. Lines 25–29 compare against that captured value. A commit-copy bug that drops or resets unrelated customer/creation/decision metadata during successful Mutate could become the expected value and pass these assertions. Initial Add/read copying has a proper independent complete-state oracle; successful mutation does not.

Action: independently construct expected successful state from the original sentinel invoice with only CustomerName changed; compare complete serialized expected state against both the Mutate result and a fresh stored read before testing retained-reference corruption and exception isolation. This exercises all eight current invoice properties at the actual commit boundary in both fake and real repository variants. No production defect in the current MemberwiseClone implementation is alleged. Agent handling: parent added independently constructed expectedCommitted and compared it against result/fresh storage; reviewer rechecked those assertions and ran the suite successfully (96/96). Participant verdict: **pending**.

### S1-TR-03 — Race success branches do not prove complete stable transition responses (medium)

Evidence: `InMemoryInvoiceRepositoryTests.cs:61` discards Submit and Approve responses; successful submit/approve branch at line 63 asserts only final status and actor. `ApproveAndReject_ExactlyOneCoherentFinalDecision` at lines 72–76 discards both returned snapshots and checks selected final fields. Consequently those cases do not assert the requested stable detached intermediate response or complete unchanged nondecision fields. A changed CustomerName/Amount/CreatedAt in a racing successful path could pass these branches; an incorrectly live Submit response could become Approved after the second transition without detection here.

Action: capture both results, assert a complete expected final state with bounded UTC decision time and unchanged nondecision fields, and check the returned Submit snapshot remains PendingApproval after a successful subsequent approval. Keep failure outcomes conditional on serial order; do not demand global unchanged state while another operation succeeds. Consider controlled serial ordering of both branches to ensure both are exercised, while retaining the simultaneous barrier race. Existing outcome logic is consistent with valid serial execution; this is a meaningful assertion gap, not an identified incorrect production ordering. Agent handling: parent now captures and completely compares submitted response after the race, and captures successful approve/delete response; final recheck confirms parent also added independent complete expected final states, bounded UTC timestamps and successful returned-winner equality in competing approvals, submit/approve, approve/reject and approve/delete. The submitted response remains independently checked as pending after the race. Agent handling: addressed and rechecked; no remaining agent finding from S1-TR-03. Participant verdict: **pending**.
